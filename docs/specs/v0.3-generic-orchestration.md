# v0.3 Generic AI CLI Orchestration Specification

Status: **Approved on 2026-07-28**

Target release: `v0.3.0`

## 1. Objective

Turn AI CLI Orchestrator from a dispatcher shaped around one maintainer's
Google, MiniMax, and Ark subscriptions into a provider-neutral orchestration
core.

The v0.3 product must let a user:

- name local AI CLI instances without changing source code;
- group workers into ordered profiles;
- map explicit task routes to capability requirements and profiles;
- invoke a worker, profile, or route through one stable `run` command;
- retain the bounded prompt, workspace, permission, timeout, process-tree, and
  diagnostic protections established in v0.2;
- keep all v0.2 commands and configuration working through the compatibility
  facade while users explicitly migrate to generic v2 routing;
- use the maintainer's current plan combination only as an optional showcase.

Generic does **not** mean arbitrary shell execution. New CLI integrations remain
reviewed source adapters shipped with a release.

## 2. Assumptions and approved constraints

These assumptions are intentionally surfaced before implementation:

1. Windows PowerShell 5.1 and PowerShell 7 remain supported with no required
   runtime dependency beyond Windows and the selected provider CLIs.
2. The v0.2 observable contract is public: commands, parameters, JSON
   `schemaVersion: 1` envelopes, default models, exit behavior, and environment
   variable overrides must remain compatible. The sole v0.3 security exception
   is raw provider stderr diagnostic content, which is replaced by a generic
   withheld diagnostic.
3. A new `run` command may introduce a new JSON `schemaVersion: 2` contract
   because it did not exist in v0.2.
4. Provider credentials stay in each provider CLI's native credential store.
   AIW configuration must never contain or print API keys, tokens, passwords,
   cookies, authorization headers, or arbitrary environment values.
5. Configuration may select only adapters compiled into the installed AIW
   version. It may not define command strings, argument templates, scriptblocks,
   hooks, raw environment maps, or external adapter code.
6. A configured worker can narrow an adapter's capabilities but can never grant
   a capability that the adapter has not been reviewed to provide.
7. Task classification remains explicit. AIW resolves a named route
   deterministically; it does not inspect prompt content to guess a route.
8. A write worker is never retried on a different worker after its process has
   started. This avoids duplicating or compounding partial repository edits.
9. Existing installed configuration is preserved. Migration is explicit,
   non-destructive, and never overwrites an existing destination.
10. The maintainer's provider order and model choices are documentation data,
    not product defaults.
11. The user-level AIW config, the user's `PATH`, installed provider binaries,
    and provider-native profile/config directories are privileged local trust
    boundaries. AIW never auto-loads repository-local config and does not claim
    to authenticate a malicious same-named binary or provider hook.

## 3. Problem statement

v0.2 already contains a reusable safe process runner and bounded work-order
transports, but provider identities leak through every public and internal
layer:

- the top-level command set is fixed to `ark`, `agent`, `google`, `minimax`,
  and `quota`;
- model override parameters are provider-specific;
- executable discovery, default models, account/profile paths, status, doctor,
  fallback, and invocation switches enumerate the same four worker names;
- `config.example.json` encodes the maintainer's exact plan combination;
- the installer copies that personal example as the default user config;
- `doctor` treats all four CLIs as mandatory rather than accepting a valid
  supported subset.

Adding another CLI or using a different subscription mix therefore requires
editing the core script. That is the coupling v0.3 removes.

## 4. Domain model

### 4.1 Adapter

An adapter is reviewed implementation code shipped with AIW. It translates a
validated request into one provider CLI invocation and normalizes its result.

Initial adapter catalog:

| Adapter ID | Intended CLI | Maximum reviewed capabilities |
| --- | --- | --- |
| `claude-code/v1` | Claude Code or a compatible endpoint used through Claude Code | `text.reason`, `workspace.read`, `workspace.write` |
| `antigravity/v1` | Google Antigravity CLI | `text.reason`, `context.long`, `workspace.read`, `workspace.write` |
| `minimax-cli/v1` | MiniMax CLI | `text.reason`, `quota.read` |

Adapter IDs are versioned so a breaking provider CLI change can be introduced
as a new adapter contract instead of silently changing an existing one.

### 4.2 Worker

A worker is a named local instance of one adapter. It supplies non-secret
settings such as:

- enabled state;
- default model;
- reviewed executable path override;
- native provider profile/config path;
- an optional subset of the adapter's capabilities.

Different accounts or models of the same CLI are represented as different
workers. The new `run` interface has no provider-specific model override.

### 4.3 Profile

A profile is an ordered list of worker IDs plus bounded read-only fallback
policy. It expresses a user's plan economics and preferences without changing
or contaminating the adapter implementation.

Profiles cannot contain profiles. This keeps resolution local and prevents
cycles.

### 4.4 Route

A route is an explicit task class that references one profile and declares:

- required capabilities;
- default mode;
- allowed modes.

Routes cannot reference routes and contain no prompt classifier. Capability
requirements are checked before provider priority.

## 5. Public CLI contract

### 5.1 New commands

```powershell
aiw run -Worker <worker-id> -PromptFile <path> -Mode read -WorkingDirectory <path> -Json

aiw run -Profile <profile-id> -PromptFile <path> -Mode read -WorkingDirectory <path> -Json

aiw run -Route <route-id> -PromptFile <path> -WorkingDirectory <path> -Json

aiw catalog -Json

aiw config -Action validate -ConfigPath <path> -Json

aiw config -Action migrate -ConfigPath <v1-path> -Destination <new-path> -Json
```

`-Worker`, `-Profile`, and `-Route` are mutually exclusive selectors.

If none is supplied, AIW may use `defaultRoute` or `defaultProfile` from an
explicit v2 config. If neither exists, it returns `SELECTION_REQUIRED`; AIW
does not silently apply a built-in provider preference.

New `run` parameters:

| Parameter | Contract |
| --- | --- |
| `-Worker` | Select exactly one configured or discovered worker. No cross-worker fallback. |
| `-Profile` | Select the first statically eligible worker from an ordered profile. |
| `-Route` | Resolve explicit capability and mode requirements, then its profile. |
| `-RequireCapability` | Optional additive capability requirements; cannot relax route requirements. |
| `-Prompt` / `-PromptFile` | Exactly one. UTF-8 file transport remains preferred for non-trivial work orders. |
| `-Mode` | Defaults to `read` unconditionally. A route may allow write but can never select it by default. |
| `-WorkingDirectory` | Existing canonical directory; adapter receives no undeclared workspace root. |
| `-TimeoutSeconds` | One total budget shared by all attempts. |
| `-MaxPromptBytes` | Optional caller-side narrowing of the configured hard limit. |
| `-ConfigPath` | Explicit config path; otherwise user-level config/discovery rules apply. |
| `-NoFallback` | Caller-side narrowing that forces one started attempt. |
| `-Json` | Emits the v2 envelope for new commands. |

Schema-v2 `run` enforces a 1 MiB hard prompt limit and returns structured
`PROMPT_INVALID` preflight evidence if a caller requests a larger ceiling. The
shared parameter binder retains the historical 16 MiB range only so schema-v1
legacy aliases do not break before reaching their frozen facade.

`-Model`, `-GoogleModel`, and `-AgentModel` remain legacy-only. A reproducible
v2 call selects a named worker whose model is part of its definition; passing a
legacy model flag to `run` fails preflight with `MODEL_OVERRIDE_FORBIDDEN`.

### 5.2 Compatibility facade

The following v0.2 calls remain accepted:

```text
status
doctor
ark
agent
google
minimax
quota
```

Their current parameters, defaults, JSON field names, `schemaVersion: 1`,
non-JSON output, and child exit-code behavior are frozen by golden tests.
This includes the historical `MaxPromptBytes` binding range; the v2 limit is
enforced after command selection rather than by narrowing the shared binder.

Internally, the facade translates them into the v2 runtime model and execution
engine. It is not a separate provider implementation.

`status` and `doctor` continue to default to the v1 output contract. An explicit
`-OutputSchema 2` exposes the generic worker inventory without changing legacy
automation.

No removal date is assigned to the legacy facade in v0.3.

### 6.1 Discovery and installation

- Upgrades preserve any existing `~/.aiw/config.json`.
- `version.json` is the single product-version source. New application and
  Codex-skill ownership markers record that version; valid schema-1 markers
  from older installations remain accepted for guarded upgrade and uninstall.
- Fresh v0.3 installs do not copy the maintainer showcase.
- If no user config exists, `catalog`, v2 `status`, and v2 `doctor` return an
  in-memory inventory of built-in adapters whose official executables are
  discoverable; this does not create a config file.
- An explicit v2 config, including one with an empty `workers` object, disables
  implicit discovery. This makes an empty config an intentional deny-by-default
  inventory rather than an ambiguous request to scan PATH.
- Discovery never creates or modifies a config file and never invents provider
  credentials, model overrides, account profiles, or a preference order.
- A discovered worker has `model: null` and delegates model choice to the native
  CLI default; inventory marks that choice as non-pinned and less reproducible.
  It can be selected explicitly. Multiple discovered workers
  without a configured default still produce `SELECTION_REQUIRED`.
- A discovered MiniMax executable is inventory evidence only: MiniMax execution
  requires an explicit v2 `region` because discovery never guesses an endpoint.

## 7. Strict configuration validation

Validation occurs completely before any worker process starts.

The validator must:

- require `schemaVersion` to be exactly `1` or `2`;
- reject config files larger than 1 MiB, nesting deeper than 20, more than 128
  workers, 64 profiles, 64 routes, or 64 reported validation errors;
- reject unknown top-level and adapter-specific fields;
- validate IDs against `^[a-z][a-z0-9._-]{0,63}$` and detect duplicates
  case-insensitively;
- reject unknown or unsupported adapter IDs;
- verify all worker, profile, and route references;
- reject profile nesting, route nesting, cycles, and empty profiles;
- require configured capabilities to be a subset of adapter maximums;
- prevent a route or call from escalating `read` to `write`;
- reject secret-like property names including `token`, `key`, `secret`,
  `password`, `credential`, `authorization`, and `cookie`;
- reject `command`, `args`, `arguments`, `template`, `script`, `shell`, `hook`,
  and arbitrary `env` fields at any depth;
- do not accept arbitrary v2 provider endpoint URLs; adapters expose bounded
  choices such as a region enum and map them to an exact compiled hostname,
  port, scheme, and path policy so credentials cannot be redirected to an
  attacker-controlled HTTPS host;
- expand and canonicalize paths without reading or printing credential values;
- restrict executable overrides to adapter-reviewed filenames and launcher
  extensions;
- sort validation errors by JSON path and return stable codes without echoing
  rejected values.

Configuration can only narrow safety. Adapter hard limits always win.

Executable filename and extension validation prevents accidental adapter
confusion; it is not binary attestation. A malicious user-level config, poisoned
user `PATH`, replaced provider binary, or malicious provider-native hook already
has the user's local execution authority and is outside AIW's isolation claim.
AIW therefore never discovers config from the working repository and reports
the resolved executable and config provenance in v2 inventory output.

Provider-native profile directories may themselves contain hooks, plugins, or
other executable configuration. Unless an adapter has a tested flag that
disables those mechanisms, the profile is a trusted local dependency rather
than part of AIW's sandbox claim. Fixed provider tools and permission flags do
not override malicious native profile code.

Schema-2 `doctor` makes a non-invasive local probe: it resolves an approved
worker executable and, for adapters that support `configDirectory`, records the
expanded directory path and whether it exists. It does not open profile files,
load hooks, inspect credentials, or contact a provider. If a selected profile
directory is absent, `run` returns preflight `PROFILE_DIRECTORY_INVALID` before
it starts a worker process.

## 8. Adapter and launcher seam

Each adapter implements the following internal contract:

```text
Describe() -> AdapterDescriptor
ValidateWorker(worker) -> ValidationIssue[]
Probe(worker, context) -> ProbeResult
Plan(request, worker, context) -> InvocationPlan
Decode(nativeResult) -> AdapterResult
```

`InvocationPlan` is internal data that cannot be constructed from JSON:

```text
filePath
arguments[]
workingDirectory
standardInputText?
temporaryArtifacts[]
environmentOverlay
launcherKind
effectiveCapabilities[]
```

Core validation runs again on every plan before launch.

Launcher invariants:

- adapters always build argument arrays, never command strings;
- `.exe` runs directly;
- `.ps1` runs through the current PowerShell host with fixed
  `-NoLogo -NoProfile -NonInteractive -File` arguments;
- `.cmd` and `.bat` fail closed by default;
- the existing MiniMax npm shim remains an adapter-private reviewed exception
  whose prompt uses a temporary file and whose model and HTTPS URLs are
  strictly validated;
- no configuration switch can enable that exception for another adapter;
- prompt content never appears in argv, arbitrary environment values, or
  diagnostics;
- the central native runner alone owns timeout, process-tree termination,
  stream draining, output separation, and cleanup.

Provider-specific safeguards remain mandatory:

- Claude Code adapters use fixed permission modes, fixed tool allowlists, and no
  session persistence;
- Antigravity adapters always use native sandboxing and register only the
  canonical workspace plus the controlled work-order directory; v0.3 exposes
  no Antigravity config-directory override because the official CLI has no
  documented mechanism for it;
- MiniMax adapters expose no workspace read or write capability.
  Their optional native profile directory maps only to `MMX_CONFIG_DIR`.

Adapter output is deliberately permissive. The central runner attempts to
decode valid stdout JSON and otherwise returns raw stdout text. Claude Code and
MiniMax request native JSON output; Antigravity requests native text output.
Those requests are not an assertion that all stdout must be valid JSON, and
invalid JSON stdout is not an `OUTPUT_INVALID` failure. Stderr is never parsed
as provider output and is not published in result diagnostics; non-empty
provider stderr produces only a generic withheld diagnostic.

## 9. Selection and fallback semantics

Resolution is deterministic:

1. Resolve the explicit selector or configured default.
2. Combine route requirements, mode-implied requirements, and caller-added
   requirements.
3. Default to `read`. A route may narrow allowed modes but cannot default to
   `write`; write always requires the caller's explicit `-Mode write`.
4. Reject an invalid mode before probing or launching.
5. Filter disabled, unresolved, launcher-incompatible, and capability-ineligible
   workers.
6. Preserve profile declaration order.
7. Launch within one shared deadline.

Static skips are reported separately and do not count as started attempts.

`read` is a side-effect ceiling, not an implicit `workspace.read` capability.
Stateless reasoning workers can satisfy a read-mode route that requires only
`text.reason`; repository routes must explicitly require `workspace.read`.

Hard fallback rules override profile configuration:

- `-Worker` never falls back to another worker.
- `-NoFallback` permits at most one started attempt.
- write mode may skip a statically ineligible worker before launch, but after
  one worker process starts it never launches another worker.
- `permission_denied`, `config_invalid`, `capability_denied`,
  `launcher_unsafe`, and `wrapper_error` never trigger fallback.
- timeout fallback is read-only, opt-in, and allowed only after confirmed
  process-tree termination with remaining total budget.
- every candidate is rechecked against the same mode, capabilities, and
  canonical workspace.

## 10. Result and error contracts

New commands use a schema v2 envelope:

```json
{
  "schemaVersion": 2,
  "productVersion": "0.3.0",
  "ok": true,
  "command": "run",
  "request": {
    "route": "repo-review",
    "profile": null,
    "worker": null,
    "mode": "read",
    "requiredCapabilities": [
      "text.reason",
      "workspace.read"
    ]
  },
  "selection": {
    "resolvedProfile": "paid-first",
    "worker": "review-primary",
    "adapter": "antigravity/v1",
    "model": "example-model"
  },
  "exitCode": 0,
  "timedOut": false,
  "readTimedOut": false,
  "outputLimitExceeded": false,
  "cleanupFailed": false,
  "terminationSucceeded": true,
  "containmentApplied": true,
  "treeTerminationConfirmed": true,
  "durationMs": 1200,
  "failureKind": null,
  "skipped": [],
  "attempts": [],
  "output": {},
  "error": null,
  "diagnostics": null,
  "warnings": []
}
```

Every public schema-v2 result includes the required top-level
`productVersion` from `version.json`, including preflight and wrapper failures.
The frozen schema-v1 facade does not gain this field.

Stable v2 exit codes:

- `0`: success;
- `1`: a started worker ultimately failed;
- `2`: request, selection, config, capability, workspace, or launcher preflight
  failure;
- `124`: final result is a process timeout;
- `125`: final result is a stream-drain timeout.

Child exit codes are recorded in attempts. Legacy aliases continue their v0.2
exit behavior.

Stable error families:

- configuration: `CONFIG_INVALID`, `CONFIG_SECRET_FIELD`,
  `ADAPTER_UNKNOWN`;
- selection: `ROUTE_NOT_FOUND`, `PROFILE_NOT_FOUND`, `WORKER_NOT_FOUND`,
  `SELECTION_REQUIRED`, `NO_RUNNABLE_WORKER`;
- preflight: `CAPABILITY_DENIED`, `WORKDIR_INVALID`, `PROMPT_INVALID`,
  `LAUNCHER_UNSAFE`, `POLICY_DENIED`, `PROFILE_DIRECTORY_INVALID`;
- execution: `PROCESS_START_FAILED`, `TIMEOUT`, `STREAM_DRAIN_TIMEOUT`,
  `PERMISSION_DENIED`, `AUTHENTICATION`, `QUOTA_OR_RATE_LIMIT`,
  `PROCESS_EXIT`, `OUTPUT_LIMIT`;
- wrapper: `WRAPPER_ERROR`.

Post-execution environment or controlled-artifact cleanup failure preserves
the real child exit code in `attempts`, sets `cleanupFailed: true`, returns
`failureKind: wrapper_error`, and uses `error.phase: cleanup`. It is never
reclassified as a before-execution failure and is never fallback-eligible.

Worker stdout is untrusted payload. Valid JSON stdout becomes structured output;
otherwise AIW returns raw text. Provider stderr is untrusted too, but is never
published in `diagnostics`; a non-empty stderr stream yields only a generic
withheld message. Structured `failureKind`, `error`, and attempt metadata are
the public automation signals.

The process runner enforces a 16 MiB bound for stdout and separately for stderr.
An overflow terminates the process tree and returns public
`failureKind: output_limit`, `error.code: OUTPUT_LIMIT`,
`outputLimitExceeded: true`, and exit code `1`, without placing captured
provider data in the structured output. Output limit is not fallback-eligible.

## 11. v0.2 migration

Schema v1 config remains for the frozen compatibility facade. Generic `run`,
generic route/profile selection require explicit migration; they do not
normalize a v1 document in memory. Schema-2 inventory reports legacy
provenance and migration guidance without manufacturing v2 workers:

```text
workers.ark     -> legacy-ark     + claude-code/v1
workers.agent   -> legacy-agent   + claude-code/v1
workers.google  -> legacy-google  + antigravity/v1
workers.minimax -> legacy-minimax + minimax-cli/v1
```

The explicit migration preserves the reviewed legacy mapping where representable:

- current default models;
- Ark's existing bounded fallback behavior;
- the separate Agent Plan native profile;
- Antigravity sandbox and workspace scoping;
- MiniMax stateless-only and quota behavior;
- legacy environment-variable path overrides;
- schema v1 status, doctor, result, and exit contracts.

`aiw config -Action migrate` writes a credential-free v2 file only to a new
destination. It fails if the destination exists and never modifies the source.

## 12. Project structure

Implementation should incrementally move the monolithic script behind a deep
module without a big-bang rewrite:

```text
ai-workers.ps1                       # CLI parser and compatibility facade
bin/aiw.ps1                          # installed launcher
src/Aiw.Core.psm1                    # single public module seam
src/Core/Configuration.ps1           # parse, validate, normalize v1/v2
src/Core/Inventory.ps1               # discovery and non-secret probes
src/Core/Routing.ps1                 # worker/profile/route resolution
src/Core/Execution.ps1               # budgets, attempts, fallback policy
src/Core/NativeProcess.ps1           # process, streams, timeout, tree kill
src/Core/PromptTransport.ps1         # UTF-8 bounded stdin/temp artifacts
src/Core/Results.ps1                 # v2 result and v1 projection
src/Adapters/ClaudeCode.ps1
src/Adapters/Antigravity.ps1
src/Adapters/MiniMaxCli.ps1
tests/unit/
tests/contract/
tests/integration/
examples/profiles/
examples/showcases/
docs/specs/
docs/plans/
```

The module exports one orchestration function for the CLI. Adapters never launch
processes directly.

## 13. Code style and engineering rules

- Keep `Set-StrictMode -Version Latest` and `$ErrorActionPreference = 'Stop'`.
- Use approved PowerShell verbs and singular nouns for functions where
  practical.
- Prefer small pure functions for parse, normalize, validate, select, plan, and
  result projection.
- Keep provider names inside adapter files and showcase/compatibility data.
- Do not use `Invoke-Expression`, command-string concatenation, implicit shell
  expansion, or unvalidated splatting from config.
- Return objects from core functions; only the CLI boundary serializes or exits.
- All temporary paths must be created under an AIW-owned random directory and
  pass a canonical namespace guard before recursive cleanup.
- Errors must use stable codes; tests must not depend only on prose messages.
- New code and fixtures are UTF-8 without BOM.

## 14. Testing requirements

Tests target public behavior first, with focused seam tests for the native
runner and adapter plans.

Required Windows PowerShell 5.1 and PowerShell 7 coverage:

1. Golden parity for every v0.2 command, parameter translation, schema v1
   envelope, default, and exit behavior.
2. Legacy v1 compatibility plus an explicit, non-destructive v2 migration;
   generic `run` must reject unmigrated v1 configuration before provider start.
3. Strict rejection of unknown fields, secret-like fields, arbitrary command
   fields, unknown adapters, capability escalation, and broken references.
4. Worker, profile, and route selection plus deterministic candidate ordering.
5. Mode and capability checks complete before any fixture process starts.
6. MiniMax can never satisfy workspace read or write.
7. Read-only fallback obeys policy and one total deadline.
8. A started write attempt never triggers another worker.
9. Permission denial never triggers fallback.
10. Unicode, multiline, quotes, backslashes, and space-containing paths survive
    transport unchanged.
11. Prompt content never appears in process argv, arbitrary env, or diagnostics.
12. Adapter golden invocation plans preserve Claude tool limits, Antigravity
    sandbox and directory registration, and MiniMax stateless file transport.
13. `.cmd`/`.bat` fail closed except the exact reviewed MiniMax shim path.
14. Stdout/stderr separation, raw-text/JSON stdout behavior, withheld provider
    stderr, output-limit containment, timeout `124`, stream timeout `125`, full
    descendant termination, and guarded temp cleanup.
15. `status`, `doctor`, and `catalog` are local, non-billable, and never print
    credential values.
16. Fresh install contains no personal model, account path, or priority order.
17. Upgrade preserves v1/v2 user configuration.

Real service smokes run only after deterministic tests. Each adapter receives an
independent bounded read smoke; a worker's self-reported success is not final
acceptance.

Final system acceptance must run in a separate fresh Codex task and prove:

- global skill discovery without current-thread assistance;
- installed source hash matches the candidate;
- the full regression suite passes;
- `doctor` returns a valid generic inventory;
- one structured, bounded, read-only worker call succeeds;
- the task reports `COLD_START_PASS` or an evidence-backed
  `COLD_START_FAIL`.

## 15. Documentation requirements

The README cognitive funnel becomes:

1. one-sentence value proposition;
2. install and a provider-neutral first run;
3. concepts: adapter, worker, profile, route;
4. supported adapter catalog and security boundaries;
5. neutral configuration examples;
6. maintainer showcase clearly labeled as one optional example;
7. v0.2 compatibility and migration;
8. contributor adapter checklist and test matrix.

The Codex skill must select by declared capability and user-configured route,
not by hardcoded provider names. It may show the maintainer profile only as an
example.

## 16. Success criteria

v0.3 is complete only when:

- a user can configure a supported subset or multiple instances without source
  edits;
- no v2 configuration, discovery, route/profile, installer, or documentation
  default encodes the maintainer's provider order or models; the frozen v0.2
  compatibility facade retains its historical defaults;
- all v0.2 regression contracts pass, with only the documented genericization
  of raw provider stderr diagnostics;
- unsupported capability requests fail before process creation;
- configuration cannot inject arbitrary commands, arguments, code, or
  environment variables beyond the explicitly documented trusted executable
  and provider-native profile boundaries;
- status/doctor work for any valid supported subset;
- tests pass on Windows PowerShell 5.1 and PowerShell 7;
- install, upgrade, migration, uninstall, and cold-start acceptance are
  independently verified;
- documentation distinguishes deterministic local probes from real online
  service acceptance.

## 17. Approval gates

Implementation starts only after the maintainer approves these public decisions:

1. `run` selects a named `Worker`, `Profile`, or explicit `Route`.
2. Models are part of worker definitions rather than the new call interface.
3. Only reviewed built-in adapters are executable; JSON cannot define shell
   commands or third-party code.
4. Legacy commands and schema v1 remain supported without a removal date.
5. The current paid-plan combination becomes a non-installed showcase.
